# Nightshift MVP

A local macOS desktop app for finding GitHub issues and running owner-initiated Codex work that can continue unattended through dependent issues, producing independent pull requests for manual review and merging.

## Planning status

The MVP uses independent execution branches and pull requests targeting the repository's default branch. An explicit GitHub dependency is a strict gate: B cannot start until its blocker A is closed. For implemented work, the team closes A after its pull request is merged. Detailed completion criteria and review phases are deferred. The workload consists of open issues assigned to the active GitHub CLI account and labeled `ready-for-agent` across added projects, with a configurable concurrency limit. Active runs automatically discover newly assigned or labeled issues. Open parents provide context rather than separate executions; closing a parent makes its entire child pile ineligible for new execution. Failure handling remains to be defined.

## Current scaffold

The initial usable scaffold lets the owner add local repositories and fetch open issues from GitHub repositories the active GitHub CLI account can access. It fetches up to ten results for the selected project at a time and provides a search field with GitHub-style qualifiers, including `label:ready-for-agent`. **Load more** follows GitHub pagination for that project. **All projects** combines results already fetched during the current session; it does not start a broader request. This browsing mode does not authorize execution or relax the run readiness rules below. Runs, executions, and publication are implemented as described below; see [docs/workflow-orchestration.md](docs/workflow-orchestration.md).

The authenticated GitHub CLI integration accepts a repository when the active account can access it and limits execution candidates to issues assigned to that account.

## Workflow

1. Add a project by selecting an existing, initialized local repository. Identify its GitHub repository from its Git remote.
2. Select a project and refresh its open issues. The first request is capped at ten results; use **Load more** when more are available. Filter the fetched results with `label:ready-for-agent` when reviewing execution candidates.
3. **Checking.** The owner starts a run over open issues assigned to the active GitHub CLI account and labeled `ready-for-agent` across added projects. Persist the candidate's checking state and verify every start-eligibility gate. Do not advance when any check fails.
4. **Working.** After checking succeeds and capacity is reserved, save the immutable issue and parent snapshots, fetch the latest GitHub default branch, create the dedicated worktree and branch from that fetched commit, run optional setup, and start Codex. Keep the execution in this step until local work reaches its terminal successful result; GitHub changes do not interrupt it.
5. **Branch published.** After local work finishes, verify the sole publication gate: the issue remains open. Push the recorded branch through the selected remote and save evidence of the exact remote branch before advancing. A closed issue preserves the local result and ends without publication.
6. **Pull request published.** Only after branch publication is recorded, create or recover the pull request for that exact branch targeting the repository's default branch and save its stable identity and URL before advancing.
7. Show the current workflow step, evidence, output, and errors. A failed check or operation remains at its current step. An explicit owner retry reruns only the incomplete transition; completed steps never run again.
8. Keep blocked issues under observation during an active run. When GitHub reports blocker A closed, reevaluate dependent issue B and start it only if every other eligibility rule also passes.

## Keyboard interface

All app workflows must be usable with the keyboard, with visible shortcut hints and focus indicators. ⌘1 through ⌘9 select projects in sidebar order; ⌘0 selects All projects. Projects beyond the ninth remain reachable through keyboard focus.

The issue search field combines text and filters. `/` or ⌘F focuses the field. Ordinary typing, selection, and clipboard editing use standard text input, without Vim modes. Search applies to fetched open issues across added projects, narrowed by the selected sidebar project. Title text and GitHub-style qualifiers such as `label:ready-for-agent`, `-label:bug`, `repo:owner/name`, and quoted label names can be combined. Show unsupported or incomplete filters explicitly rather than silently ignoring them. Enter in search or ⌘R refreshes only the selected project and fetches its first page; **Load more** fetches its next page. Esc moves focus to results without clearing the query. Arrow keys and `j`/`k` browse results outside the field, and Enter opens an issue. Tab and Shift-Tab reach other controls.

This is a local search over fetched open issues, not a GitHub-wide search or an implementation of every GitHub qualifier. It does not expand execution eligibility.

## Updates

Release builds check for a newer release on their own channel at startup and then hourly, through the authenticated GitHub CLI. Nightshift downloads and verifies the update in the background, then offers **Restart to update** in the sidebar, with a keyboard shortcut. It never installs or restarts without the owner's action. Restarting stops active work the same way quitting does, so while a run or execution is active it requires a second confirmation. See [docs/releases.md](docs/releases.md#updates).

## Rules

- The owner starts unattended work. While a run is active, Nightshift automatically refreshes open issues assigned to the active GitHub CLI account and labeled `ready-for-agent` across all added projects, starting eligible work as capacity becomes available, including issues assigned or labeled after the run began. Manual search remains available.
- Refresh GitHub immediately when a run starts, whenever an execution finishes and capacity becomes available, and every five minutes otherwise while the run remains active. Allow manual refresh without resetting that schedule. Never overlap refreshes. Do not poll automatically without an active run, and back off after rate-limit or transient GitHub failures.
- Keep closed issues out of the active candidate list. Fetch a closed issue only when needed to evaluate a parent or dependency relationship. Show completed execution history from Nightshift's local database rather than treating closed GitHub issues as active workload.
- Treat execution start as the remote-state boundary. Start eligibility includes every required GitHub and local gate: open state, run owner, repository access, assignment, readiness, parent state, dependencies, push preflight, and any other precondition. Once local execution starts, GitHub changes and failures—including logout, account switching, access loss, label or assignment changes, parent closure, issue closure or deletion, and rate limiting—never pause or cancel it. Preserve completed local work when publication cannot proceed.
- Model the complete lifecycle as one persisted, monotonic workflow: checking → working → branch published → pull request published. Each transition validates its prerequisite, performs only its own operation, and atomically saves the resulting evidence and audit event before the next transition may begin. On failure, remain at the current step with the error. Only an explicit owner action retries that incomplete transition; never replay a completed step or skip ahead.
- Give every workflow step an explicit step policy that declares whether occupying it consumes an execution slot. The orchestrator must evaluate this policy before entering the step. `checking`, `branch published`, and `pull request published` do not consume a slot; `working` does. Acquire capacity atomically with entry into a slot-consuming step, wait without advancing when capacity is unavailable, and release capacity only after safely leaving the final contiguous slot-consuming step. Future steps must declare the same policy rather than adding special-case slot logic.
- Keep step policies fixed in the typed application code for the MVP. Settings controls only the numeric concurrency limit; users cannot edit whether a step consumes capacity, and the database does not define or reconfigure the workflow.
- Store recoverable failure as an error on the current workflow step, not as a generic failed step. Persist the attempted transition, available evidence, diagnostic detail, and retry availability. An explicit owner retry reruns that transition; after success, clear the error atomically with the new evidence and state, then resume orchestration. Interruption ends the current local attempt but permits explicit continuation of the same workflow.
- Only explicit owner shutdown or a terminal local condition may stop an active execution. Terminal local conditions include setup failure before Codex launch, Codex exit, owned-process crash, and operating-system or machine shutdown. Remote GitHub conditions are never terminal for local execution.
- GitHub CLI must be installed and authenticated before Nightshift performs repository verification, issue discovery, eligibility refreshes, or remote writes. Nightshift never falls back to anonymous GitHub requests; GitHub API usage is charged to the active user's authenticated rate limits.
- Accept any public or private GitHub repository that the active GitHub CLI account can access. Reject repositories that account cannot access. Repository access alone does not enroll a project; the owner must still add it through the project workflow.
- Revalidate project access before starting new work. If access is unavailable, start no new executions for that project and continue eligible work in other accessible projects. If publication fails, retain the worktree, branch, output, and error for manual recovery; do not switch accounts or silently retry remote writes. The general execution rule protects work already in progress.
- GitHub CLI installation and login are owner-managed prerequisites. In the MVP, Nightshift only diagnoses a missing CLI or invalid session and asks the owner to configure it outside the app; Nightshift does not install `gh`, launch `gh auth login`, request scopes, or repair authentication.
- Git push authentication is also an owner-managed prerequisite. Nightshift does not run `gh auth setup-git` or modify global or repository credential configuration. It uses the selected remote's existing SSH or HTTPS setup; publication failure preserves the completed local branch under the remote-state rule.
- Verify push capability for the selected remote non-destructively before reserving an execution slot. Failed verification or authentication that would require an interactive prompt blocks new executions for that project without consuming capacity; unrelated projects continue and the general execution rule protects active work.
- Require direct push access to the selected repository for the MVP. Do not create or discover forks, add fork remotes, or create pull requests from cross-repository heads. A read-only selected remote fails push preflight and blocks new execution for that project.
- Before GitHub operations, validate that the installed GitHub CLI supports the exact commands and structured fields Nightshift requires. Do not rely only on a hard-coded version threshold. Missing capabilities block GitHub operations and require the owner to update `gh` outside the app.
- Capture the active GitHub CLI identity as the run owner when a run starts. Before every new execution, confirm that GitHub CLI remains authenticated as that identity. If authentication fails or the active account changes, start no new executions and require the owner to restore the original identity or end the run; the general execution rule protects work already in progress.
- An issue must be assigned to the active GitHub CLI account and have `ready-for-agent` itself. Assignment identifies the accountable owner whose GitHub access Nightshift uses; the label delegates that issue to Nightshift. If the issue has a parent issue, that parent must also have `ready-for-agent`; a missing or unverifiable parent label prevents a start. This readiness requirement does not make the parent a dependency or require it to finish first.
- Multiple assignees are independent accountable owners. If the active GitHub CLI account is one of them, no additional approval is required; each assignee may execute the issue independently and publish a separate pull request through their own account. Closing the issue prevents new executions but does not interrupt local work already in progress.
- Publication eligibility has one workflow gate: the execution's issue must remain open after local work finishes. Do not recheck assignment, labels, parent state, or dependencies. If the issue is closed, do not push the branch or create a pull request; retain the local branch, worktree, output, and reason publication was skipped. Do not modify a pull request that was already opened before the issue closed.
- If Nightshift cannot verify the issue's open state, or if push or pull-request creation fails, stop that publication attempt and record the error. Do not infer eligibility, retry automatically, or publish later as a side effect of automatic discovery. Preserve the local result and require an explicit owner-requested publication recheck before any further remote action.
- Expose **Recheck publication** on the affected execution. The action first verifies that the issue remains open, stops again if it is closed or unverifiable, and otherwise resumes the incomplete publication work. Normal issue search and active-run refresh are read-only with respect to publication and never trigger this action.
- Readiness depends only on the required label being present. Do not inspect or restrict who applied `ready-for-agent`; repository permissions and the team's GitHub workflow govern label authority.
- Do not require a parent issue to be assigned to the active GitHub CLI account. In a team workflow, a senior owner may retain the parent while its executable children are assigned to other accountable owners. Evaluate assignment only on the child that would receive an execution.
- Open parent issues provide context for their child executions and are not executed separately. If a parent closes, do not start any of its remaining children and do not modify those children on GitHub. The general execution rule protects a child already in progress. Who closes an open parent after its children finish remains to be settled.
- A closed parent resolves a dependency on that parent regardless of the states of its children. The closed parent's own children remain ineligible because their parent is closed.
- A child's eligibility includes both its own explicit dependencies and its open parent's explicit dependencies. If parent P depends on parent Q, P's children wait until Q closes. If P closes first, its children leave the candidate workload.
- Each execution starts from the latest fetched default branch and publishes an independent pull request targeting that default branch. PR stacking, `gh stack`, predecessor-branch bases, and cross-teammate stack coordination are outside the MVP. Sharing a parent does not serialize children; otherwise eligible children may run concurrently within the global limit.
- Use GitHub's explicit "blocked by" relationships as the source of issue dependencies. Shared parents and references in descriptions or comments do not create dependencies. The owner maintains these relationships in GitHub.
- For an executable issue, a dependency is resolved when its blocking issue is closed. For implemented work, closure means its pull request has been merged; the owner or team maintains this GitHub lifecycle. Nightshift uses the issue's closed state as the dependency signal and does not introduce a separate PR-merge lookup gate. A finished local execution or unmerged branch never permits dependent work to start. An open or unverifiable prerequisite remains blocking; the owner manually corrects obsolete or incorrect relationships in GitHub.
- Settings controls the concurrency limit: the maximum number of executions in progress across all projects combined. This limits simultaneous work, not the total number of issues in a run. Fill available slots with eligible issues as executions finish. Prevent duplicate active executions of the same issue.
- Use the saved description for the execution. The local database owns execution state and retains a basic history of state changes.
- Keep agent changes in the issue's worktree, separate from the owner's original checkout.
- Quitting Nightshift stops active executions, including any preparation work. Preserve their saved output, history, branches, and worktrees, and record stopped executions as interrupted. Do not resume them automatically.
- Interrupted executions remain available for inspection after reopening Nightshift. Provide **Retry working** to continue the same execution from its saved working step, retaining the worktree, branch, issue snapshot, and history. Confirm the previous owned process has stopped and acquire concurrency capacity before resuming. Never resume automatically or replay completed steps. If continuation cannot be established, retain the interruption and report the error.
- Scope includes unattended progression, required checks and automated review phases, branch publication, and independent PR creation. Final human review and merging remain manual. Do not add scheduled starts, issue editing, a code editor, automatic recovery, or cleanup. An explicit owner-requested publication recheck is not automatic recovery. Limits for fixing review findings and retrying failed phases are still to be decided.
